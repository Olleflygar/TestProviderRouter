## Problem

Metrics history is currently queried for the entire recent window and aggregated mainly by provider name. The default DuckDB database is shared at `~/.nygen_router/metrics.duckdb`. Reusing a display name across applications, environments, models, protocols, provider accounts, endpoints, credentials, or configurations can blend unrelated history and produce incorrect routing scores.

Provider name is also used by health and diagnostic structures. Once duplicate display names are allowed, name-only health, attempts, exclusions, errors, and restart records become ambiguous.

Streaming telemetry has a related semantic flaw: `stream=True` currently means a stream successfully opened. A requested streaming call that fails before opening is recorded as a failed regular call. Streaming scoring consequently misses the failure, while regular history may incorrectly receive it.

PR29 establishes explicit scope, stable provider identity, declared call type, and unambiguous streaming observations before global/shared storage work continues.

## Authoritative identity model

### Required provider identity

Add a required, nonblank, stable `provider_id: str` field to `ProviderConfig`.

`provider_id` is the canonical identity wherever program behavior must distinguish configured providers:

- metrics recording and matching;
- aggregation and scoring;
- health state;
- health reports and reset operations;
- provider attempts;
- eligibility and exclusion records;
- fallback and restart records;
- provider-specific exception attributes;
- internal dictionaries, sets, and lookup keys.

Reject duplicate provider IDs within one `ProviderRouter` before any routing work. The error must name every duplicated ID without exposing secrets.

`ProviderConfig.name` remains required and nonblank but becomes display metadata. Duplicate names within one router are valid. Recommend distinct names in documentation, but do not enforce uniqueness.

Where duplicate names could make diagnostics ambiguous, logs, errors, reports, and callbacks must expose both display name and provider ID. For example:

```text
Provider "OpenAI" (id="openai-project-a") timed out
```

Retain provider names in public diagnostic records where they help humans, but never use them as identity or filtering keys.

Separate provider IDs are expected for distinct performance or failure domains, including different:

- provider accounts;
- API-key quota domains;
- deployments;
- gateways;
- endpoints that should learn independently.

Do not record, hash, compare, or expose API keys. Users distinguish credentials through explicit provider IDs.

The same provider ID may intentionally appear in different metrics scopes. This enables explicitly requested cross-scope history sharing.

Changing display name alone preserves history. Changing model or protocol creates a different metrics partition. Changing base URL alone does not automatically create a different partition; assigning a new provider ID is how a user declares a different account, endpoint, deployment, quota, or failure domain.

### Required metrics scope

Add a required, nonblank, plain-string `metrics_scope` configuration to `ProviderRouter`.

Prefer a required keyword argument so callers must specify it explicitly without silently falling into a shared default:

```python
router = ProviderRouter(
    providers=[...],
    metrics_scope="customer-support:production",
)
```

Every newly recorded event must contain a non-null scope. There is no unscoped event-writing mode and no default `"global"` or `"default"` scope.

Add a public `HistoryScope` enum with at least:

```python
HistoryScope.CURRENT
HistoryScope.ALL
```

`ScoreBasedPolicy.history_scope` defaults to `HistoryScope.CURRENT`.

- `CURRENT` reads only events matching the router’s current required `metrics_scope`.
- `ALL` deliberately ignores scope during reads and combines otherwise matching provider partitions across every recorded scope.
- `ALL` affects reading only. Events written by that router still contain its configured scope.

Export new public types consistently from the package root without adding optional import dependencies.

## Declared call type

Add a public required enum to `CallVariant`:

```python
class CallType(StrEnum):
    REGULAR = "regular"
    STREAMING = "streaming"
```

Every `CallVariant` must explicitly declare `call_type`; there is no default.

Example:

```python
CallVariant(
    protocol=ApiProtocol.OPENAI_CHAT,
    operation="chat.completions.create",
    call_type=CallType.STREAMING,
    arguments={
        "messages": [...],
        "stream": True,
    },
)
```

The router must never inspect native arguments to infer, validate, inject, or reconcile call type. In particular, do not read `arguments["stream"]`. The caller owns consistency between `CallVariant.call_type` and native provider arguments.

Approved clarification: a mismatch between declared `call_type` and native
arguments/adapter return shape is caller misconfiguration and is outside the
guaranteed telemetry-classification contract. Preserve existing returned-object
handling, do not inspect arguments, and do not synthesize new validation or
fallback behavior for this edge case.

Continue passing `CallVariant.arguments` through unchanged except for the existing model injection. Document `call_type` as router metadata, not request-shaping configuration.

All variants supplied to one `ProviderRouter.invoke()` must declare the same call type. Fallback must never change a caller from a regular response contract to a streaming response contract or vice versa.

Validate this before contacting a provider. Add a narrow typed router error, following the existing `DuplicateCallVariantProtocolError` and transparent-error patterns, for mixed call types. It must describe the conflicting protocols/call types without inspecting arguments or leaking secrets.

Place the invocation’s call type in frozen `RoutingContext`.

Remove `ScoreBasedPolicy.use_streaming` as a public configuration source. The policy must automatically score the partition matching `RoutingContext.call_type`. Do not retain two independently configurable settings that can contradict each other.

## Metrics partition

For score-based routing, matching observations are identified by:

```text
metrics_scope, when HistoryScope.CURRENT
+ provider_id
+ model
+ protocol
+ CallVariant.call_type
```

When `HistoryScope.ALL` is selected, scope is intentionally omitted from matching, while every other dimension remains required.

These are not PR29 partition dimensions:

- provider display name;
- base URL;
- operation string;
- capabilities or tools;
- request-size bucket.

Request-size bucket is reserved in the schema by this PR but becomes a matching/scoring dimension only when PR11 implements its producer and routing behavior.

## Streaming telemetry semantics

For every attempt, distinguish:

- `call_type`: what the caller declared;
- `stream_opened`: what the router observed;
- `success`: whether the attempt ultimately succeeded;
- completion/interruption through the existing stream machinery.

Required cases:

| Declared call type | Stream opened | Result | Recorded classification |
| --- | --- | --- | --- |
| Regular | Not applicable | Success/failure | `REGULAR`, `stream_opened=None`, real success |
| Streaming | No | Opening failure | `STREAMING`, `stream_opened=False`, `success=False` |
| Streaming | Yes | Mid-stream failure | `STREAMING`, `stream_opened=True`, `success=False` |
| Streaming | Yes | Completed | `STREAMING`, `stream_opened=True`, `success=True` |

A `NormalizedStream` returned by an adapter establishes `stream_opened=True`. A declared streaming attempt that fails before such a return records `False`.

Continue recording streaming outcomes at the point the outcome is known, not at stream opening. Preserve existing `RouterStream` completion, failure, restart, truncation, close, and health timing unless explicitly changed here.

### Timing

- Regular successful `latency_ms` remains full-response latency.
- Streaming `latency_ms` always means time to first chunk.
- If no first chunk arrives, streaming `latency_ms` is `NULL`.
- Never repurpose streaming `latency_ms` as time until failure.
- `total_duration_ms` records elapsed attempt time to streaming completion or failure, including failure before a stream opens.
- Streaming successes with `latency_ms=NULL` do not contribute `0`; they are excluded from average TTFT.
- Failed attempts never contribute to average latency or TTFT.
- They still contribute to attempt count, failure rate, error tallies, health, and scoring evidence as appropriate.
- Preserve the current rule that a stream’s success is decided at observed completion, not opening.

Do not inspect native arguments to verify that declared call type matches the actual provider request. Caller configuration is authoritative. Continue using observed returned shape only for `stream_opened` and existing stream control flow.
