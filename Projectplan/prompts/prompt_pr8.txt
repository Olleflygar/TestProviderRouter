Design decisions already made for you

These were settled in the 2026-07-23 design interview and folded into the
plan's PR 8 section. Implement them exactly:

1. What was deliberately dropped, and why (do not re-add any of these):
   - recent_error_count is not read anywhere in this PR. Within one
     lookback window it is mathematically attempt_count * (1 -
     success_rate) -- fully derivable from success rate, which the score
     already uses -- and it is volume-sensitive in a way success rate is
     not (a provider tried more often would look worse at an identical
     rate). It remains available on ProviderStats purely as a diagnostic
     stat.
   - There is no separate "exploration bonus" toggle or code path. The
     optimistic-start blend in decision 3 below IS the mechanism that
     lets new/thin-history providers get tried -- it is always on, for
     every provider, unconditionally.
   - Rate-limit hits are not a scoring input. They are already excluded
     by hard filtering while active, and their effect on success rate is
     already captured once eligible again; do not add any rate-limit-
     specific penalty.

2. ScoreWeights (new file src/nygen_router/scoring.py) -- a Pydantic
   model, matching the codebase's existing config-model style (see
   HealthConfig in health.py for the pattern: model_config =
   ConfigDict(extra="forbid"), field_validator for range checks):

   class ScoreWeights(BaseModel):
       model_config = ConfigDict(extra="forbid")
       success_weight: float = 1.0
       speed_weight: float = 1.0
       regular_latency_reference_ms: float = 2000.0
       streaming_ttft_reference_ms: float = 500.0
       optimistic_start: float = 0.75
       optimistic_start_pretend_attempts: float = 5.0

   Validation: success_weight and speed_weight must each be >= 0.
   regular_latency_reference_ms and streaming_ttft_reference_ms must each
   be > 0. optimistic_start must satisfy 0 <= value <= 1.
   optimistic_start_pretend_attempts must be > 0. Additionally, a
   model_validator(mode="after") rejects the combination
   success_weight == 0 and speed_weight == 0 (both zero simultaneously)
   -- the weighted average in decision 4 would be undefined with a
   zero denominator. Exactly one of the two weights being 0 is valid and
   must be accepted (it simply drops that component's influence).

3. ProviderScore (src/nygen_router/scoring.py) -- a frozen dataclass, not
   Pydantic (internal record, per Core design principle 7):

   @dataclass(frozen=True)
   class ProviderScore:
       provider_name: str
       total: float
       success_quality: float
       speed_quality: float

   Keep success_quality and speed_quality on the result, not just total
   -- a low score must be explainable from its own components, not a
   black box.

4. calculate_provider_score (src/nygen_router/scoring.py):

   def calculate_provider_score(
       stats: ProviderStats,
       weights: ScoreWeights,
       *,
       use_streaming: bool = False,
   ) -> ProviderScore:

   Step 1 -- pick fields: if use_streaming is True, use
   stats.streaming_attempt_count, stats.streaming_success_count,
   stats.streaming_success_rate, stats.streaming_avg_ttft_ms, and
   weights.streaming_ttft_reference_ms. If False, use the regular_*
   equivalents and weights.regular_latency_reference_ms.

   Step 2 -- success_quality via the blend formula:
       blended = (pretend * optimistic_start + real_count * observed)
                 / (pretend + real_count)
   where pretend = weights.optimistic_start_pretend_attempts, real_count
   = the picked attempt_count, observed = the picked success_rate (treat
   None as 0.0 -- with real_count == 0 in that case the formula's own
   weighting makes the observed value irrelevant, producing exactly
   optimistic_start). Do not write a separate branch for "no data" --
   this formula must handle it by construction.

   Step 3 -- speed_quality: first convert the picked avg_latency_ms to a
   raw quality value (treat None as producing raw quality 0.0, again
   irrelevant once blended with real_count == 0):
       raw_quality = reference_ms / (reference_ms + latency_ms)
   using the picked reference_ms from step 1. Then blend this raw_quality
   toward optimistic_start using the SAME formula as step 2, but with
   real_count = the picked success_count (not attempt_count -- latency
   only exists for successful/completed attempts, so success_count is
   the right evidence size here).

   Step 4 -- total via weighted average, never a plain sum:
       total = (weights.success_weight * success_quality
                + weights.speed_weight * speed_quality)
               / (weights.success_weight + weights.speed_weight)
   ScoreWeights' own validation (decision 2) guarantees this denominator
   is never 0.

   Return ProviderScore(provider_name=stats.provider_name, total=total,
   success_quality=success_quality, speed_quality=speed_quality).

New test file tests/test_scoring.py. Minimum coverage -- implement all of
these:

- holding every other field fixed, a higher regular_success_rate
  produces a higher total score than a lower one
- holding every other field fixed, a lower regular_avg_latency_ms
  produces a higher total score than a higher one
- a ProviderStats with regular_attempt_count == 0 and
  regular_success_count == 0 (and the corresponding rate/average both
  None) scores success_quality == speed_quality == optimistic_start
  exactly, for use_streaming=False; the streaming mirror for
  use_streaming=True
- a provider with a real attempt count well below
  optimistic_start_pretend_attempts scores noticeably closer to
  optimistic_start than its raw observed success_rate would suggest; a
  provider with an attempt count well above
  optimistic_start_pretend_attempts scores close to its raw observed
  success_rate (assert with an explicit tolerance, not exact equality)
- setting speed_weight=0 makes the total score depend only on
  success_quality (vary speed inputs and see no change); the symmetric
  case for success_weight=0; constructing ScoreWeights with both weights
  at 0 raises a validation error
- calling with use_streaming=True reads only the streaming_* fields
  (construct a ProviderStats with very different regular_* and
  streaming_* values and assert the two use_streaming settings produce
  different, field-appropriate scores)
- total is within [0, 1] across a spread of valid weights and stats
  combinations, including edge cases (zero attempts, very high latency,
  a 100% success rate at low latency)
- ScoreWeights: default construction succeeds with no arguments; each of
  the six fields' invalid values (negative success_weight, negative
  speed_weight, zero regular_latency_reference_ms, zero
  streaming_ttft_reference_ms, optimistic_start outside [0, 1], zero or
  negative optimistic_start_pretend_attempts) is individually rejected
