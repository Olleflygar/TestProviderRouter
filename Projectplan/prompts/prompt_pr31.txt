## Outcome

Make one ProviderRouter instance safe to share across threads within a single
process, and give the router a defined end of life. Concretely:

- Both bundled metrics stores become thread-safe within one process by
  serializing all database access behind one lock per store instance.
- All mutable router state — health, the default adapter cache, policy
  ordering, and the warning/drop counters — is protected by one router lock.
- Provider network calls remain fully concurrent: no lock is ever held across
  an adapter invocation or while a stream is being consumed.
- ProviderRouter gains close() and context-manager support. Close is
  idempotent and terminal for the router, and closes only the store the
  router itself created.
- A support matrix in ProviderRouter/README.md declares exactly what is and
  is not supported.

PR31 deliberately does not add buffered/batched writes (PR32), native async
(PR33), multi-process DuckDB coordination, cross-process health sharing
(PR25/PR14), or a graceful-drain close that waits for outstanding streams.

## Store-level serialization

Give DuckDBMetricsStore and SQLiteMetricsStore the identical treatment: one
threading.Lock per store instance, held for the full duration of every
database operation — lazy connection creation (including existing-schema
validation and fresh-database creation), record_attempt, query_recent,
query_score_aggregates, the private explain helper, and close. The lock is
never held during any non-database work.

For SQLite, create the connection with check_same_thread=False. This is safe
precisely because the store lock now guarantees the connection is only ever
used by one thread at a time; state that constraint in the code where the
connection is created.

Store close semantics are unchanged: close releases the connection now, is
idempotent, and a later operation lazily reconnects. Do not make the stores
terminal, do not add per-thread connections, and do not change any public
store signature. Direct users of a store class continue to see exactly
today's behavior, now safe from any thread.

## Router-level serialization

Add one threading.Lock to ProviderRouter guarding all of its mutable state:

- the _health dictionary and every ProviderHealthState mutation (including
  the read-modify-write in record_failure reached through the router);
- the default adapter cache, so exactly one adapter is ever created per
  provider;
- the metrics warning/recovery flags, the dropped-events counter, and the
  stream-shape warning set; and
- the call to policy.order(), so built-in policies (including
  RoundRobinPolicy's index and ScoreBasedPolicy's warning flag) need no
  internal locks of their own.

Health reads for eligibility filtering and health_report(), and health writes
from both the regular path and RouterStream's deferred recording, all go
through the same lock.

Never hold the router lock (or any lock) across an adapter invocation, a
stream's chunk iteration, or any provider network activity. Lock acquisition
order is always router lock before store lock when both are needed; the
score-based policy's aggregate read during ordering therefore runs under the
router lock and takes the store lock inside it. Keep every critical section
short and document the ordering rule where the locks are defined.

The documented policy contract becomes: the router always invokes
policy.order() while holding its lock, so custom policies are automatically
serialized per router instance and must not call back into the router.

## Close and lifecycle

Add ProviderRouter.close() plus __enter__/__exit__ context-manager support.

Ownership: close() closes the metrics store only when the router constructed
it — the unset-default DuckDB case. A caller-provided store (including
metrics_store=None) is the caller's to close; the router must not touch it.

Terminality: close() is idempotent, and after it completes the router is
finished. A subsequent invoke() raises a new clearly named error from the
existing NygenRouterError hierarchy (for example RouterClosedError extending
ConfigError or NygenRouterError — follow the hierarchy's conventions) whose
message states the router was closed. reset_health() and health_report()
after close may keep working on the in-memory state; do not add errors there.

The straggler rule: the router's internal metrics-recording path checks the
closed flag under the router lock. After close, a metrics write coming from a
still-draining RouterStream (or any late bookkeeping) is dropped and counted
through the existing dropped-events counter at DEBUG — it must not reach the
store, must not lazily reopen the closed connection, and must not emit the
"metrics storage is unavailable" warning. The stream itself keeps flowing
untouched, and its in-memory health update still lands. Never interrupt an
in-flight call or stream from close(); close does not wait for them.

Closing while another thread holds a lock simply waits its turn; the store
lock already guarantees close cannot interleave with a write in progress.

Export the new error and any new public surface following the package's
existing export conventions.

## Support matrix documentation

Add a "Concurrency and lifecycle" section to ProviderRouter/README.md,
alongside the existing health and metrics sections, containing a clear
support matrix. It must state at minimum:

Supported:
- one ProviderRouter shared by multiple threads in one process — health,
  policy ordering, adapter reuse, and metrics recording are serialized;
- provider network calls running fully concurrently across threads;
- DuckDBMetricsStore and SQLiteMetricsStore used from multiple threads in one
  process;
- several processes sharing one metrics database via SQLiteMetricsStore; and
- close() as an idempotent, terminal end of life, with with-statement usage.

Not supported (each with its one-line reason and, where applicable, the PR
that owns it later):
- multiple processes writing one DuckDB file (DuckDB is single-writer;
  use SQLite);
- sharing health state across processes (in-memory by design; PR25/PR14);
- one stream consumed by more than one thread (streams are single-consumer);
- using the router after close() (raises; late stream bookkeeping loses only
  its metrics row, never stream content); and
- buffered/batched writes and native async (eager per-attempt writes remain;
  PR32/PR33).

Also state the shutdown rule plainly: finish calls and fully drain or close
streams before closing the router; a stream finishing after close drops
exactly its one metrics row, visibly counted.
