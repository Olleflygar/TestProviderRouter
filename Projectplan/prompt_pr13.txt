## Version metadata and baseline

Introduce one deliberately small metadata table named:

`nygen_router_schema_versions`

Its logical schema is:

```text
component TEXT PRIMARY KEY
version   INTEGER NOT NULL
```

Version stored components independently. PR13 creates the `metrics` component
at integer version `1`. A later PR may add `health` as a separate row and
revision stream. Runtime metrics validation reads only the `metrics` revision;
it must tolerate and preserve other well-formed component rows rather than
coupling unrelated schemas.

Keep the metadata table's schema and version constants in one authoritative
location. The latest creation DDL, runtime validation, administration
inspection, and migration registry must agree. Unknown metadata-table shapes,
duplicate/invalid component records, nonpositive/noninteger revisions, a
missing required metrics row, and a metrics revision newer than the installed
package are actionable incompatibilities.

### Fresh database behavior

- If the configured local database path is absent, normal first use by
  `DuckDBMetricsStore` or `SQLiteMetricsStore` may create the parent directory,
  the exact current `provider_attempts` schema, and the version table with

- Creation must complete transactionally where supported. Do not leave a

- Every later run reuses the same configured path and validates it; it must not

- DuckDB's omitted-path behavior remains the stable default
  `~/.nygen_router/metrics.duckdb`.
- SQLite continues to require the explicit path its constructor currently
  requires.

### Existing database behavior during normal runtime

- An existing, correctly versioned version-1 database is validated and reused
  without DDL.
- An existing `provider_attempts` table that exactly matches today's approved

- If an existing path has an absent, partial, extra, reordered, mistyped, or

## Separate administration API

Add a typed public administration module under the storage package, for
example `nygen_router.storage.admin`, with exactly these conceptual operations:

- `inspect_database(...)`
- `create_database(...)`
- `migrate_database(...)`

Use an explicit typed local-backend selector with only DuckDB and SQLite. Do
not accept arbitrary backend strings deep in the implementation or leak native
connections. Functions should accept `str | Path` targets. An omitted path may
mean the stable default only for DuckDB; reject an omitted SQLite path.

Return frozen typed result records containing the information callers need.
Raise focused typed administration/schema errors with actionable messages.
The Python API must not print or log routine success output.

Keep this API separate from `MetricsStore`, `ProviderRouter`, and policy
construction. It operates directly on a deliberately selected database target
and never makes provider calls.

### `inspect`

`inspect` is strictly read-only:

- report the backend and fully resolved path;
- report whether the path exists and whether it is DuckDB's default path;
- do not create a missing file or parent directory;
- report the metadata-table state and every valid component revision;
- distinguish a fresh/missing target, implicit unversioned baseline, current
  version, supported older version, unsupported/unknown schema, and
  newer-than-installed version;
- report compatibility and the next safe action;
- never acquire a write connection merely for convenience.

Prove with tests that inspecting an absent path creates nothing and inspecting
an existing target changes neither schema nor rows.

### `create`

`create` means only "create a completely new database":

- require an absent target;
- create the current metrics schema and `metrics = 1` metadata atomically;
- validate the result before reporting success;
- refuse any existing filesystem target, including an empty or incompatible
  database, and leave it byte-for-byte/schema-for-schema untouched;
- do not offer `--force`, overwrite, replace, delete, archive, move, redirect,
  or automatic alternate-name behavior;
- do not import or copy history from another database.

If an existing database occupies the desired path, tell the user to inspect
it, migrate it when supported, manually move/archive it while the application
is stopped, or choose a different path and update router configuration.

If creation itself fails after this operation created a brand-new target,
clean up only that provably operation-owned partial target when it is safe to
do so. Never delete a target that predated the call.

### `migrate`

`migrate` means only "upgrade this existing database through known version
steps":

- require an existing target;
- support the exact current unversioned schema as the implicit version-1
  baseline and explicitly stamp it with `metrics = 1`;
- treat a correctly versioned current database as a successful no-op;
- build and validate the complete ordered migration route before writing;
- accept no version gaps, guessed transforms, or migrations from unknown
  shapes;
- reject a database newer than the installed package;
- update the version row only after the corresponding schema/data step has
  succeeded, in the same transaction;
- roll back the whole attempted migration on failure and never continue to a
  later step;
- preserve unrelated valid component rows;
- be idempotent when invoked again after success.

Create a small ordered migration registry/mechanism that future PRs can extend
one version step at a time. Do not invent fake historical metrics schemas or a
fake v0 data transformation merely to demonstrate the mechanism. The real
PR13 migration is explicit stamping of the exact implicit baseline; every
future schema-changing step must bring its own forward-migration and tests.

### Offline and failure-safety contract

Administration migration is offline. Require documentation and errors to say
that the application, routers, and other database writers must be stopped.
Acquire the backend-appropriate exclusive transaction/lock and fail safely if
the target is busy; do not promise online migration or add PR31 concurrency
work.

Use transactional DDL/data changes supported and verified against each real
engine. A migration failure must leave the original schema version and history
usable. If an engine operation cannot satisfy the required atomicity, stop and
report the architectural conflict rather than weakening the guarantee.

Backups are never automatic. `migrate_database` and the CLI may accept one
optional, explicit backup destination for local databases:

- the source must first pass the supported-input inspection;
- refuse an existing backup target;
- create the backup using an engine-safe offline method, not an unsafe live
  file copy;
- validate that the backup is readable and represents the pre-migration
  source before changing the source;
- if backup creation/validation fails, leave the source untouched;
- retain a successful backup even if the subsequent migration fails;
- never select a default backup filename or generate repeated backup files.

Do not add a general backup/restore product or cross-backend export/import.
