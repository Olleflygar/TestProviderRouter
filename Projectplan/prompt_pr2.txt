Known deviations from the plan (read carefully)

The plan's PR 1 section says RouterResponse already carries `attempts` and
`excluded` fields. In the real code it does not: PR 1 shipped without them,
and the ProviderAttempt / EligibilityResult types do not exist anywhere.
PR 2 must therefore add all of this now:

- EligibilityResult and ProviderAttempt types (see types below)
- RouterResponse.excluded: list[EligibilityResult] — populated with real
  content on every call; this is PR 2's core job
- RouterResponse.attempts: list[ProviderAttempt] — schema added now so PR 3
  does not need a breaking change to a public response type; in PR 2 it
  always contains exactly one entry (the single provider actually invoked)

Also present in the current code: capabilities.py has
validate_request_capabilities() raising CapabilityError, called from
ProviderRouter.invoke(). PR 2 retires that path (see control flow below).

⸻

Goal

Before routing, filter the whole provider list down to providers that can
satisfy the request, and make every exclusion transparent to the caller.

Important principle: hard filters are not scores. A provider that cannot
support tools is EXCLUDED for a tool request, never ranked lower.

⸻

filters.py (new module: src/nygen_router/filters.py)

Implement:

- FilterReason: an enum of exclusion reasons (per the plan's
  enums-for-capability-flags principle). Cover at least: provider disabled,
  API key unavailable, protocol unsupported, missing tool-calling support,
  missing streaming support, missing JSON-mode support.

- EligibilityResult: one record per excluded provider, carrying the provider
  name, its FilterReason, and a specific human-readable detail string
  (e.g. "missing tool-calling support").

- filter_eligible_providers(...): takes the full provider list and the
  request, returns the eligible providers and the exclusions (one
  EligibilityResult per excluded provider). Essential filters:

  * provider enabled
  * API key available (resolvable from api_key or a populated api_key_env —
    check without raising and without exposing the key)
  * protocol supported by the router (only OPENAI_CHAT has an adapter today)
  * model configured
  * tool-calling support, if request.requires_tools
  * streaming support, if request.requires_streaming
  * JSON mode support, if request.requires_json_mode

- RequestRequirements: the plan lists this type in PR 2 scope. Implement it
  as a small internal record (dataclass, per the plan's typing principles)
  derived from RouterRequest if it makes the filter interface clearer. If
  passing RouterRequest directly is cleaner, that is acceptable — state the
  choice and its reason in your completion report.

⸻

types.py additions

- ProviderAttempt: provider_name, success flag, and the real underlying
  error object if the attempt failed — the actual exception, never a
  router-rephrased summary. None on success.

- EligibilityResult and ProviderAttempt appear on the public RouterResponse,
  so prefer Pydantic models for consistency with the rest of types.py. Note:
  holding a real exception object in a Pydantic field requires allowing
  arbitrary types on that model's config.

- RouterResponse gains two fields, both defaulting to empty lists (use
  default_factory):
    attempts: list[ProviderAttempt]
    excluded: list[EligibilityResult]

⸻

Router control flow change (router.py)

invoke() changes from "pick the first enabled provider, then validate
capabilities against only that one" to:

1. Filter the whole provider list with filter_eligible_providers.
2. Among eligible survivors, select the first (no rotation — that is PR 3).
3. Invoke it via the adapter, as today.
4. Return a RouterResponse whose `excluded` lists every filtered-out
   provider with its specific reason (populated on EVERY call, success or
   not) and whose `attempts` contains exactly the one invoked provider.

CapabilityError is retired from the invoke() path — it must no longer be
reachable from a normal invoke() call. If nothing references CapabilityError
or validate_request_capabilities after the refactor, remove them and update
their tests to the new behavior. This is the deliberate, plan-sanctioned
behavior change described in the Testing philosophy; it is not a license to
weaken unrelated tests.

If filtering excludes every configured provider, raise
NoEligibleProvidersError (new, in errors.py, inside the existing exception
hierarchy). Per the transparency principle, its message must enumerate every
excluded provider with its own specific reason, e.g.
"provider_a: missing tool-calling support; provider_c: disabled" —
never a single blended "no eligible providers" message.

Keep NoProvidersConfiguredError for the empty-provider-list case.
