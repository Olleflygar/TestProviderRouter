## Approved PR26 behavior

PR26 adds an optional `StickyRoutingPolicy` wrapper that gives an explicitly
configured ordered list of provider IDs fixed priority over the providers
ordered by another policy.

This is the intended composition:

```text
hard eligibility and health filtering
    -> eligible sticky providers in configured sticky-ID order
    -> remaining eligible providers in wrapped-policy order
    -> existing router fallback/fail-fast loop
```

For example, if the eligible providers are `a`, `b`, `c`, and `d`, the sticky
IDs are `["a", "b"]`, and the wrapped policy orders the non-sticky remainder
as `[d, c]`, the final attempt order is `[a, b, d, c]`.

If `a` is filtered out, the prefix starts with `b`. If no sticky provider is
eligible for a call, the wrapped policy entirely determines the order among
the eligible remainder. If every eligible provider is sticky, the sticky
configuration order is the complete attempt order.

The policy must never receive or resurrect a hard-filtered provider as a valid
attempt. Health and eligibility always override fixed preference.

### What “sticky” does and does not mean

The policy does not record that a prior call or scope succeeded on a provider.
It does not observe attempt outcomes and does not store mappings such as
`conversation-123 -> provider-a`. Each invocation computes its preferred prefix
from the same fixed configuration.

Consequently, PR26 has:

- no affinity key;
- no user, session, conversation, workflow, or request identity abstraction;
- no learned affinity state;
- no per-model, protocol, operation, `CallType`, or `metrics_scope` preference
  records;
- no TTL, idle timeout, absolute age, successful-use budget, or refresh rule;
- no use of the router's clock for sticky behavior;
- no affinity store, persistence, process-restart recovery, distributed state,
  cleanup, eviction, maximum-entry setting, reset, clear, or manual-replacement
  API;
- no post-success or post-failure policy-notification protocol.

Those omissions are deliberate consequences of the approved fixed-preference
design, not unfinished pieces of PR26. Do not add them.

The configured preference applies to every invocation made through the router
using that policy. Different calls still see different eligible sets. For
example, a preferred `OPENAI_CHAT` provider is absent when a call supplies only
an `OPENAI_RESPONSES` variant, and a disabled, keyless, auth-benched, or
cooling-down preferred provider is likewise absent.

Applications that require different preferred-provider lists for different
users, conversations, workflows, or logical models should create separate
router/policy instances or supply their own custom policy. Do not introduce a
framework-specific identity abstraction into the core.

### Purpose and guarantees

Consistently trying a chosen provider first may improve the chance of reusing
provider-local prompt caches or concentrate traffic toward provider/account
usage tiers and quotas. The router does not inspect prompts, detect cache
support, determine account-tier boundaries, or guarantee any provider-side
cache hit, token top-up, quota, or tier benefit.

Health filtering and fallback can intentionally send a call elsewhere. The
documentation must not present fixed preference as a correctness guarantee for
provider-owned response IDs, conversations, stored responses, or other state
that requires the exact originating endpoint/account. Explain that callers
still own strict provider affinity when correctness—not merely preference—is
required.

## Public API

Implement the policy in:

`ProviderRouter/src/nygen_router/policies/sticky.py`

Use this exact public construction shape as the primary documentation example:

```python
router = ProviderRouter(
    providers=providers,
    metrics_scope="my-app",
    policy=StickyRoutingPolicy(
        sticky_provider_ids=["provider-a", "provider-b"],
        fallback_policy=ScoreBasedPolicy(),
    ),
)
```

The compact default-remainder form is:

```python
router = ProviderRouter(
    providers=providers,
    metrics_scope="my-app",
    policy=StickyRoutingPolicy(
        sticky_provider_ids=["provider-a"],
    ),
)
```

The constructor contract is:

```python
StickyRoutingPolicy(
    *,
    sticky_provider_ids: list[str],
    fallback_policy: Policy | None = None,
)
```

- Selecting `StickyRoutingPolicy` through the existing `policy=` seam is the
  only enablement mechanism.
- Stickiness remains disabled when another policy, or no explicit policy, is
  supplied to `ProviderRouter`.
- `fallback_policy=None` creates a fresh `RoundRobinPolicy` for that sticky
  policy instance. Never use a shared mutable default policy object.
- Accept the ordered IDs as a typed list, not a raw configuration dictionary.
- Make and retain a defensive list copy so later mutation of the caller's list
  cannot silently change routing behavior. Do not require a tuple or expose
  internal mutable state.
- Do not add `StickyRoutingConfig`, a `sticky=` router option, an enum toggle,
  factory auto-enablement, or a per-call override.
- Export `StickyRoutingPolicy` from
  `ProviderRouter/src/nygen_router/policies/__init__.py` and
  `ProviderRouter/src/nygen_router/__init__.py` without adding optional imports
  or new dependencies.

Keep `Policy` itself as the existing `order(eligible, context)` protocol. Do
not add success/failure notification methods to it, change `RoutingContext`, or
modify `RoundRobinPolicy` and `ScoreBasedPolicy` behavior merely for PR26.

## Configuration validation

Use the existing `ConfigError`/`NygenRouterError` hierarchy for every new
sticky-policy configuration failure.

At `StickyRoutingPolicy` construction:

- require `sticky_provider_ids` to be a list;
- require at least one entry;
- require every entry to be a string;
- for a non-string entry, raise a clear `ConfigError` explicitly stating that
  sticky provider IDs must be strings. Do not coerce it, let `.strip()` fail,
  or misreport it merely as an unknown provider;
- strip surrounding whitespace from each string before storing and comparing
  it;
- reject empty or whitespace-only IDs;
- reject duplicate IDs after trimming and name the duplicates;
- never accept or compare provider display names as substitutes for IDs.

At `ProviderRouter` construction, after the router has copied and validated its
provider list and rejected duplicate configured provider IDs:

- validate a selected `StickyRoutingPolicy` against the router's complete
  configured provider-ID set;
- reject every sticky ID that is not configured on that router;
- raise `ConfigError` at construction time and name all unknown IDs so typos do
  not silently disable the intended preference;
- never expose API keys or secrets in the error;
- allow a known sticky provider to be disabled or currently unhealthy. Those
  are valid configurations whose runtime usability remains the filters' job.

Use a narrow validation method owned by `StickyRoutingPolicy` and invoked by
`ProviderRouter` when that policy is selected. Do not broaden the base
`Policy` protocol or redesign the entire policy system to validate PR26.

The current public `router.providers` list may be changed by callers after
construction. Runtime ordering must therefore derive the sticky prefix only
from providers present in that invocation's eligible list. If a preferred
provider is later removed or disabled, skip it. If the same canonical ID is
later restored and becomes eligible, its configured preference naturally
returns. Do not add mutation watchers or sticky state cleanup.

## Ordering algorithm and wrapped-policy contract

`StickyRoutingPolicy.order(eligible, context)` must:

1. Work only from the already-filtered `eligible` list it receives.
2. Build a canonical lookup by `ProviderConfig.provider_id` from that list.
3. Build the sticky prefix in exact `sticky_provider_ids` configuration order,
   including only IDs present in that eligible lookup.
4. Build the eligible non-sticky remainder while preserving its incoming order
   for the wrapped policy to inspect.
5. Call `fallback_policy.order()` exactly once with a fresh list of that
   non-sticky eligible remainder and the unchanged `RoutingContext`, including
   when the remainder is empty.
6. Preserve the wrapped policy's returned ordering, deliberate omissions, and
   duplicates.
7. Verify that every returned provider ID belonged to the eligible non-sticky
   remainder supplied to the wrapped policy. If it introduces a sticky,
   unknown, disabled, unhealthy, or otherwise non-input provider, raise a clear
   `ConfigError` before any adapter is invoked.
8. Use the canonical provider object from the eligible remainder for each
   validated returned ID rather than trusting a foreign `ProviderConfig`
   object with the same ID. This keeps hard-filter bypass structurally
   impossible.
9. Return the sticky prefix followed by the validated wrapped-policy result.

Do not require the wrapped policy to return an exact permutation. A custom
policy may intentionally omit providers to cap its attempt set, and PR26 must
preserve that supported trust-based behavior. Likewise, preserve duplicates
returned by a custom policy rather than using PR26 to impose a new global
policy contract. PR26 itself must never add a duplicate or implement a retry
budget; explicit same-provider retry policy remains PR27's concern.

If the wrapped policy itself raises, preserve current policy error behavior.
Do not swallow or translate arbitrary custom-policy exceptions as an
observability convenience.

## Retry, health, and fallback semantics

Do not modify the router's global rules.

- The complete order is computed before the first attempt, exactly as today.
- A retryable failure from preferred provider `a` proceeds to preferred
  provider `b`, if present and eligible, then through the wrapped-policy tail.
- A 429 or auth failure applies the existing immediate bench behavior.
- Timeout, connection, server, stream-interruption, and unknown failures keep
  using the existing counted-failure threshold and cooldown behavior.
- A preferred provider below the failure threshold remains eligible and is
  tried first again on the next invocation. PR26 adds no separate suppression
  or cooldown.
- STOP categories retain the existing global fail-fast rule even when another
  preferred or remainder provider is available. STOP failures continue to
  leave health untouched.
- A successful fallback provider does not replace, refresh, clear, or otherwise
  affect fixed preference. The next invocation again starts with the first
  configured sticky provider that is then eligible.
- If every provider returned in the composed order fails, retain the existing
  `RouterExhaustedError` and its real per-attempt failures.
- Providers omitted by a custom wrapped policy are not attempted; do not add
  them back after exhaustion.
- Same-provider retry budgets remain wholly out of scope for PR26.

## Regular and streaming calls

No regular or streaming outcome changes sticky configuration because there is
no learned state.

Regular calls:

- Use the composed provider order.
- A successful `adapter.invoke()` returns the exact raw response and changes no
  sticky state.
- A failed preferred attempt follows the existing category and fallback rules.

Streaming calls:

- Use the same composed order computed before the first attempt.
- Returning a `NormalizedStream` still records neither success nor failure at
  stream open.
- Successful completion at stream end continues to record metrics and health
  success, but changes no sticky state.
- Empty, interrupted, failed, or silently truncated streams retain the existing
  error classification and health behavior.
- Under `StreamFailurePolicy.RESTART`, `RouterStream` continues through the
  remaining composed order already carried by the stream wrapper.
- Under `StreamFailurePolicy.RAISE`, it records the existing failure and raises
  without fallback.
- STOP categories stop under either streaming policy.
- A RESTART that lands on another provider and later succeeds does not alter
  the next invocation's fixed preference.
- `close()` and bare-break semantics remain unchanged: no outcome invented, no
  restart on close, and no sticky state to update.
- Raw chunks, usage objects, and provider SDK response identity remain
  unchanged.

Do not inspect `CallVariant.arguments` to detect streaming, prompts, cache
keys, conversations, models, tools, or any other sticky dimension.

## State, lifetime, and concurrency

`StickyRoutingPolicy` stores only validated configuration and its wrapped
policy. It has no learned or expiring routing state.

- No affinity data lives on `ProviderRouter`, in health state, in the policy,
  in metrics storage, or in a new store.
- No process-restart or multi-process behavior needs implementing.
- No external service or database is required.
- The sticky-ID defensive copy is not mutated after construction.
- Sticky-prefix computation is read-only and requires no lock.
- Concurrent calls independently compute the same configured prefix from their
  own already-filtered eligible lists.
- Thread safety and mutable state inside the wrapped policy remain that
  policy's responsibility. Do not add locks to `RoundRobinPolicy`,
  `ScoreBasedPolicy`, or arbitrary custom policies as part of PR26.
- Reusing one `StickyRoutingPolicy` instance across routers shares its fixed ID
  configuration and its wrapped policy instance, but no sticky history.
  Document that separate policy instances per router are recommended because a
  wrapped policy such as round robin may itself be stateful.

Async support remains out of scope because the router core is synchronous.

## Required behavior matrix

Implement and document these scenarios explicitly. Items from earlier PR26
brainstorming that depended on learned affinity are marked not applicable so
they are not accidentally reintroduced.

1. **Sticky policy not selected:** current default or explicitly supplied
   policy behavior is byte-for-byte/semantically unchanged.
2. **No prior affinity:** prior affinity is not a concept. Eligible configured
   sticky IDs lead immediately, followed by wrapped-policy order.
3. **Preferred provider succeeds:** return its raw response; store no sticky
   state. It leads later calls because configuration is fixed.
4. **Later call through the same router:** prefer the same first configured ID
   if eligible, without consulting prior outcomes.
5. **Different application/user/conversation/workflow:** the same router-wide
   policy configuration applies. Use a separate router/policy or custom policy
   when different preferences are required.
6. **Preferred provider remains healthy and eligible:** keep it in the sticky
   prefix.
7. **Preferred provider becomes unhealthy:** existing auth bench, 429 cooldown,
   or threshold cooldown filters it out; continue with the next eligible item.
8. **Preferred provider fails another hard filter:** it is absent and cannot be
   reintroduced by either the sticky wrapper or wrapped policy.
9. **Preferred provider is disabled or removed:** skip it. Restoring it with
   the same `provider_id` restores its fixed priority when eligible.
10. **Expiration:** not applicable; no TTL or stored affinity exists.
11. **Preferred provider fails and fallback succeeds:** return the fallback
    result; future fixed preference is unchanged.
12. **Fallback fails:** continue through the remaining composed order or raise
    the existing exhausted error.
13. **Retryable versus STOP failure:** existing cross-provider fallback versus
    global fail-fast rules remain authoritative.
14. **Concurrent calls:** each computes the same fixed prefix safely; there is
    no last-writer, refresh, or affinity race.
15. **Different models, protocols, operations, or call types:** no separate
    preference records exist. Existing hard filtering determines whether each
    configured preferred provider can serve that invocation.
16. **Regular success:** raw response identity preserved; no policy state
    transition.
17. **Streaming open and successful end:** no outcome at open; existing success
    at stream end; no policy state transition.
18. **Streaming failure and RESTART:** continue through the already-composed
    remaining order; a later success does not rewrite preference. Preserve
    zero-chunk and partial-stream rules.
19. **Affinity key missing/empty/invalid:** no affinity-key API exists, so this
    is not a supported input or validation surface.
20. **Cleanup or eviction:** not applicable because there are no affinity
    entries.

PR26 emits no new observability signal for any row in this matrix.

- a counted failure below the threshold leaves the preferred provider first on

- an expired health cooldown makes a preferred provider eligible and first
  again without any sticky reset;
- removing or disabling a preferred provider skips it; restoring the same ID
  restores its priority.

### Fallback and errors

- a retryable preferred-provider failure falls back to the next preferred
  provider and then to the wrapped-policy remainder;
- a successful fallback does not change later fixed preference;
- repeated failures preserve existing attempt order and exhaustion details;
- bad request, invalid operation/arguments, and missing SDK STOP paths remain
  globally fail-fast even when other preferred providers remain;
- STOP failures do not change health;
- existing real error objects and messages remain transparent.

### Return identity and streaming

- a successful normalized stream uses the preferred order, passes chunks

- a partial/interrupted preferred stream follows existing RESTART behavior
  through the remaining composed order;
- a zero-chunk preferred stream remains a failure and can restart;
- `StreamFailurePolicy.RAISE` still prevents restart;
- STOP-category streaming failure remains fail-fast;
- a successful restarted provider does not change the next invocation's fixed
  preference;
- early close and bare break keep their existing recording semantics.

### Concurrency and regressions

- concurrent invocations using a thread-safe fake wrapped policy independently
  produce the same sticky prefix without state corruption;
- concurrent calls with different eligible protocol sets do not reintroduce
  filtered preferred providers;
- no TTL, affinity-key, persistence, or cleanup machinery is introduced;
- default `ProviderRouter` behavior and direct `RoundRobinPolicy`,
  `ScoreBasedPolicy`, and custom-policy behavior remain unchanged when the
  sticky wrapper is unused;
- the existing complete test suite continues to pass.

Avoid tests that assert provider-side caching actually occurs. The router can
control only attempt order.
