## Exact aggregate arithmetic

For each matching event, SQL computes one weight.

Flat mode:

    weight = 1.0
    since = reference_time - lookback_hours

Exponential mode:

    since = reference_time - (6 * half_life_hours)
    age_hours = (reference_time - event.timestamp) in hours
    weight = 0.5 ** (age_hours / half_life_hours)

Preserve the shipped six-half-life window and formula. Use the one captured
reference_time for the whole query; never call now repeatedly per event or let
the database choose its own current timestamp. Keep backend-specific timestamp
and exponent syntax private and prove equivalent semantics across engines.

For the selected call type and exact partition, calculate:

- attempt_weight: SUM(weight) over every matching event;
- success_weight: SUM(weight) over successful matching events;
- successful_latency_weight: SUM(weight) only where success is true and
  latency_ms is not NULL;
- successful_latency_total_ms: SUM(weight * latency_ms) over that same
  successful non-NULL-latency subset;
- recent_error_count: exact unweighted count of failed matching events;
- rate_limit_count: exact unweighted failed-event count whose error_type is
  ErrorCategory.RATE_LIMIT.value; and
- timeout_count: exact unweighted failed-event count whose error_type is
  ErrorCategory.TIMEOUT.value.

Use explicit conditional aggregation and COALESCE so a requested provider with
no events returns zeros, not NULL aggregate fields. Failed latency never
contributes. A successful NULL latency contributes success evidence but no
latency weight or total.

Derive in shared Python:

    success_rate =
        None when attempt_weight is zero
        otherwise success_weight / attempt_weight

    average_latency_or_ttft =
        None when successful_latency_weight is zero
        otherwise successful_latency_total_ms / successful_latency_weight

Build the selected regular or streaming ProviderStats bucket from these values
and leave the other bucket at its established zero/None values. Take
provider_name from the current ProviderConfig. Then use the unchanged
ScoreWeights and calculate_provider_score logic to derive success quality,
speed quality, and total score.

Keep aggregate_stats(events, providers, call_type, weight_fn=...) public and
pure. It remains the semantic oracle for tests and direct Python aggregation,
including its general callable weight_fn. ScoreBasedPolicy no longer calls it
for persisted scoring.

## Self-correction and malformed results

A valid new provider is represented explicitly:

    provider-b -> zero attempts, zero successes, zero latency evidence,
                  zero diagnostic tallies

That explicit record produces the existing optimistic-start score. Once
attempts are recorded, subsequent queries include their success/failure
evidence and scoring self-corrects.

A missing record is never interpreted as zero history. This guards against,
for example, buggy SQL that groups only successful-latency rows and therefore
omits a provider with twenty failures and no successes. Filling that omission
with zeros would repeatedly make the failing provider look new and optimistic.

Validate every result before scoring:

- exactly one record for every requested provider ID;
- no missing, duplicate, or unexpected provider ID;
- all weighted fields are real, finite, and non-negative;
- success_weight does not exceed attempt_weight, allowing only an appropriate
  tiny floating-point tolerance;
- successful_latency_weight does not exceed success_weight with the same
  care;
- successful_latency_total_ms is finite and non-negative;
- diagnostic tallies are non-boolean, exact non-negative integers; and
- zero latency weight produces no average rather than a fabricated 0.0.

Any invalid aggregate set invalidates the complete scoring read. Do not use
partial results, assign missing providers zero or worst scores, or mix trusted
and untrusted rows.
