## Shipped Chat adapter behavior that PR12 must match

Before implementing, inspect the current files and Git history rather than
assuming this summary is exhaustive. Preserve these established behaviors:

- The OpenAI SDK is lazily imported.
- `openai.OpenAI` receives the configured API key, base URL, timeout, an
  injectable `http_client`, and `max_retries=0`; cross-provider fallback is the
  router's retry mechanism.
- The router chooses the matching `CallVariant` by protocol, copies its opaque
  arguments, and injects the selected provider's model without mutating the
  original variant.
- Dotted SDK operation dispatch is resolved dynamically with `getattr`.
- Invalid operation paths and incompatible keyword arguments become transparent
  router errors with their original `AttributeError` or `TypeError` chained.
- SDK timeouts, connections, HTTP statuses, and other SDK errors map onto the
  router error hierarchy without losing provider messages, structured fields,
  response bodies, or original exceptions.
- Non-streaming success returns the real typed SDK response untouched.
- SDK streams are wrapped behind `NormalizedStream`; yielded SDK objects remain
  unchanged and unbuffered.
- Stream wrappers observe completion markers and usage, map mid-iteration
  transport/SDK failures, and propagate `close()`.
- `RouterStream` owns stream fallback, restart visibility, metrics, health,
  time-to-first-chunk, total duration, empty-stream handling, silent truncation
  detection, and close semantics.
- A successful stream is recorded only when its outcome is known, not when it
  merely opens.

The Chat adapter arrived through the provider-native API redesign in commit
`790a03f` and gained first-class streaming in commits `35544ef` and `3a9c587`.
Use those changes and the current source/tests to understand the intended seams.

Implement a distinct Responses adapter and Responses stream wrapper, using names
consistent with:

- `OpenAIResponsesStream`
- a focused module such as
  `ProviderRouter/src/nygen_router/adapters/openai_responses.py`

Keep shared OpenAI SDK client construction, dynamic dispatch, and exception

stream-wrapper hook in the existing adapter is acceptable when it prevents
duplicating the Chat adapter's behavior. Do not broadly redesign or rename the
working Chat adapter, and do not break its public or tested behavior.

Required adapter behavior:

1. Use the existing `openai` optional dependency and lazy imports. If the
   minimum declared OpenAI SDK version is too old to provide `responses.create`
   and the typed events used by the implementation, raise the existing lower
   bound to the earliest version the implementation actually supports while
   retaining the project's compatible upper-bound policy. Add no new runtime
   dependency.
2. Configure the SDK client equivalently to the Chat adapter, including the
   public injectable HTTP-client seam used by tests and `max_retries=0`.
3. Resolve `responses.create` through the same dotted-operation dispatch
   convention. The guaranteed public operation surface for this PR is
   `responses.create`.
4. Pass `CallVariant.arguments` through unchanged except for the router's
   established model injection. Do not translate Chat `messages` into Responses
   `input`, invent a shared request schema, normalize tools, or reshape
   structured-output configuration.
5. Return a non-streaming `openai.types.responses.Response` object untouched on
   an ordinary successful call. Native SDK conveniences such as `output_text`
   remain available because the original object is returned.
6. Support every native `responses.create` input that the selected installed
   SDK/provider accepts, including text and multimodal input, instructions,
   tools and function calls, structured output, reasoning options, continuation
   fields, and streaming. The router must not inspect those opaque arguments.
7. Preserve the Chat adapter's timeout, connection, HTTP, missing-SDK,
   unsupported-operation, invalid-argument, verbatim-message, structured-field,
   and exception-chaining behavior.
8. Do not claim support for `responses.retrieve`, `responses.delete`,
   `responses.cancel`, response input-item listing, or other stored-resource
   management operations. Do not strip the router-injected model to make those
   operations work.

### Provider-owned state boundary

Response IDs and conversation IDs are owned by the provider endpoint/account
that created them. Retrieval, deletion, cancellation, and history management
must remain the caller's responsibility through that exact provider's native
SDK client.

Fields such as `previous_response_id` or provider-owned conversation IDs may
pass through `responses.create`, but the router does not promise that a later
call will select the same provider. Document that stateless calls are safe
across interchangeable providers, while stateful continuation requires the
caller to preserve provider affinity or manage provider-owned state outside the
router.

Do not add response-ID tracking, provider-affinity persistence, lifecycle APIs,
or sticky routing. Background `responses.create` may pass through natively, but
PR12 does not route the later retrieve/cancel lifecycle.

## Responses streaming semantics

Responses streaming uses typed server-sent events, not Chat Completion chunks.
Yield ordinary native SDK streaming events in order and unchanged. Do not
buffer, concatenate, convert, or normalize them.

The Responses stream wrapper must understand the API's terminal shapes:

### `response.completed`

- Recognize it as terminal success.
- Mark the normalized stream completed.
- Retain the terminal response's native usage object when present.
- Yield the native event unchanged.

### `response.incomplete`

This is an explicit terminal, served result, not a transport failure or a
silently truncated stream.

- Recognize it as terminal and prevent stream-interruption fallback.
- Yield/return the native event or response unchanged.
- Retain native usage when present.
- Do not retry, fall back, bench the provider, or synthesize
  `ProviderStreamInterruptedError`.
- Under the existing binary metrics contract, record the provider attempt as
  served/successful, matching the Chat adapter's current treatment of terminal
  finish reasons such as `length`.
- Emit exactly one visible standard-logging `WARNING` for every incomplete
  response, streaming and non-streaming. Include the provider name, model,
  response ID when available, and `incomplete_details.reason`. Do not include
  request content or secrets.
- Current typed reasons include `max_output_tokens` and `content_filter`.
  Preserve an unknown/future reason rather than crashing.
- For a naturally exhausted stream, emit the warning after streamed output
  where feasible. Correctness and exactly-once visibility take precedence over
  an impossible guarantee about stdout/stderr display ordering. Never call
  `print()` from library code.

### `response.failed` and `error`

These are provider-declared failures, not successful terminal data.

- Convert them into a transparent router error that preserves the native typed
  event, embedded response when present, provider error code, message, parameter
  when present, provider name, and model.
- Add a narrowly named Responses-specific `ProviderError` subclass if needed.
  Do not invent an HTTP status for an in-stream event, and do not set a typed
  SDK event as `.original` because it is not an exception. Expose it on a clear
  structured attribute instead.
- Categorize only codes whose meaning is clear:
  rate-limit codes as `RATE_LIMIT`, explicit server failures as
  `SERVER_ERROR`, explicit timeout codes as `TIMEOUT`, and invalid
  prompt/input/configuration codes as `BAD_REQUEST`. Unknown or future codes
  remain `UNKNOWN`. Preserve the exact provider code/message regardless of
  category.
- Apply the existing router fallback, metrics, health, and stream-restart rules
  for the resulting category. `BAD_REQUEST` remains a global fail-fast category
  and must not bench the provider.
- Ensure failures raised while iterating remain within the router error
  hierarchy and retain any real exception as `__cause__`/`.original` where an
  exception actually exists.

### Missing or unfamiliar terminal event

- Any recognized Responses event establishes that the wrapper understands the
  stream shape.
- If a recognized Responses stream yields at least one event but ends without
  `response.completed`, `response.incomplete`, or a declared failure/error,
  treat it as a silently interrupted stream through the existing
  `ProviderStreamInterruptedError` path.
- A zero-event stream remains a failed attempt under the existing empty-stream
  contract.
- Preserve existing behavior for a genuinely unfamiliar shape: do not invent a
  failure without evidence, and retain the existing deduplicated warning
  behavior where applicable.
- Propagate `close()` to the underlying SDK stream and preserve current
  idempotent/context-manager semantics in `RouterStream`.

Apply equivalent status handling to non-streaming `Response` objects where the
SDK returns an explicit `completed`, `incomplete`, or `failed` status:
completed returns raw; incomplete returns raw with the required warning; failed
raises the transparent Responses-specific router error. Do not normalize queued
or in-progress background responses; return them natively and document the
provider-affinity limitation.

## Implementation phase 2: preserve and verify global fail-fast behavior

The originally proposed cross-protocol fallback correction has been explicitly
withdrawn. Do not implement protocol-scoped continuation for bad calls.

The agreed reason is:

> Invalid operations, incompatible arguments, missing SDKs, and HTTP 400/422
> responses are treated as likely caller or protocol-configuration defects that
> should surface immediately during development rather than being hidden when
> another protocol variant succeeds. This prevents a misconfigured preferred
> path from silently being replaced by a secondary provider in a long-running
> workflow. These failures do not bench the provider. General pre-flight
> validation was then expected to improve how early they were detected in
> PR22 (later scrapped), but
> cross-protocol recovery from them is intentionally out of scope.

Only after the Responses adapter and its focused tests are implemented and
passing, add/adjust regression coverage proving the existing behavior remains
intentional and consistent.

Preserve global stopping for:

- `ErrorCategory.BAD_REQUEST` (currently HTTP 400/422)
- `ErrorCategory.INVALID_OPERATION` (including unsupported operation, invalid
  operation arguments, and missing required SDK)

Verify all three router paths:

1. ordinary non-streaming fallback in `ProviderRouter.invoke`;
2. an active normalized stream failure in `RouterStream._fail`; and
3. failure while opening a replacement stream in `RouterStream._restart`.

Required regression expectations:

- A stop-category failure from an OpenAI Chat variant does not try an available
  Responses provider.
- A stop-category failure from a Responses variant does not try an available
  Chat provider.
- The same behavior holds for streaming restart paths.
- The real failure remains visible through the established direct or aggregate
  error surface and metrics record.
- Stop-category failures never change provider health or bench the provider.
- `StreamFailurePolicy.RAISE` continues to prevent mid-stream regeneration.
- Retryable failures such as timeout, connection failure, 429, auth, 5xx, and
  unknown errors still fall back across protocols, selecting each provider's
  matching `CallVariant`, operation, arguments, and model.

Do not pull the then-planned PR22 pre-flight validation into PR12. PR22 was
later scrapped.
