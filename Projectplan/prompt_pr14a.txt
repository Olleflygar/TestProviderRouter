## Outcome

Add a public, optional PostgresMetricsStore that implements the existing
three-method MetricsStore contract against PostgreSQL, so an organization can
share routing history across machines and applications. It is a live scoring
source: ScoreBasedPolicy reads its aggregates on the routing hot path exactly
as it does for the local backends. DuckDB remains the local default and
SQLite remains the native minimal option.

The whole PR is additive. It changes no file under the router core: the
router already accepts any object exposing the three storage methods, and it
only ever closes a store it created itself, so a caller-supplied PostgreSQL
store is never touched by the router's lifecycle. Do not modify router.py,
health.py, filters.py, the policy modules, scoring.py, stats.py, metrics.py,
or types.py.

PR14A deliberately does not add durable provider health (that was PR25 plus a
PR14B PostgreSQL implementation, and is not a prerequisite here), buffered or
batched writing (PR32), native async (PR33), reporting queries (PR28),
retention, rollups, caching, or any copying of local history into PostgreSQL.

## Approved design decisions

### Scope and role

PostgreSQL is the live scoring source, selected through `metrics_store=`. It
is not an analytics-only destination. Do not build a composite store, a
telemetry sink, dual writes, mirroring, or replication, and do not
synchronize or import an existing DuckDB or SQLite file. Selecting the
PostgreSQL store begins from the history already present in that database;
empty history produces explicit zero aggregates and the established
optimistic start, exactly as it does locally.

One router uses exactly one store. No backend switching, fallback chaining,
or hidden secondary writes.

### Driver and dependencies

Use psycopg 3 directly with psycopg_pool for pooling. Do not add SQLAlchemy,
any ORM, any query builder, or Alembic. The three SQL statements are held as
text in the source, the way both local backends already hold theirs, so all
three backends can be read side by side and their arithmetic compared, and so
EXPLAIN measures exactly the text that runs.

Add a `postgres` optional-dependency extra containing psycopg (binary
distribution) and psycopg_pool, with version ranges chosen and verified by
you rather than guessed. Add the extra to the `dev` extra so the test suite
can exercise it. Local users installing no extra, or only `duckdb`, must
never receive or import these packages.

Constructing the store without the extra installed follows
DuckDBMetricsStore's shipped precedent: detect availability at construction,
log one clear warning naming the exact install command, and raise a clear
ImportError from the first operation that needs the driver. Do not raise from
the constructor.

Reuse storage/base.py's shared event/record conversion so enum values, null
handling, booleans, timestamps, and field names have one source across all
three backends. Note that psycopg uses a different parameter placeholder than
sqlite3 and duckdb, so the shared insert SQL constant cannot be reused
character-for-character; derive the PostgreSQL statement from the same shared
column-name tuple rather than hand-copying the column list.

### Schema, provisioning, and versioning

The router never creates, alters, stamps, migrates, reindexes, or drops the
remote schema — not at construction, not on first use, not ever. Provisioning
is a deliberate administrative act performed with an administrator
connection, and the application's runtime role holds only INSERT and SELECT
on the attempts table plus SELECT on the version table.

Provide both provisioning routes:

- Extend the existing typed administration surface and the
  `nygen-router storage ...` CLI to accept PostgreSQL as a target for
  inspect and create, taking a connection string instead of a path. Preserve
  the shipped safety semantics exactly: creation refuses to overwrite an
  existing table, inspection writes nothing, and every failure raises from
  the existing StorageAdministrationError hierarchy with the established exit
  codes. Migration remains registered-route-only, and there are no routes to
  register yet.
- Publish the CREATE TABLE statement as a readable constant alongside the
  existing DDL constants in storage/schema.py, and document it so operators
  with their own migration tooling can apply it without installing or running
  anything of ours.

Physical schema: TEXT primary key id, TIMESTAMPTZ timestamp, TEXT for scope,
provider id, provider name, model, protocol, call type and error type,
BOOLEAN for success and stream_opened, DOUBLE PRECISION for the two latency
columns. Do not use PostgreSQL enum types. Timestamps are stored as real
TIMESTAMPTZ values rather than the local ISO-text representation; normalize
to UTC on write and return timezone-aware UTC on read, so the round trip is
behaviorally identical to the local backends.

Versioning reuses the shipped mechanism unchanged: the same version table
holding independent component rows, with the metrics component at the current
version. Do not introduce a second version concept or a parallel migration
history.

Indexes are earned, not assumed. Ship a benchmark script under benchmarks/
following benchmarks/pr30_score_aggregation.py's shape, measure the current-
and all-scope aggregate plans against realistic row counts with EXPLAIN,
retain only the smallest index set that measurably helps, and validate those
project-owned definitions in the schema check the way the SQLite index
already is. If no index measurably helps, ship none and record that, exactly
as DuckDB did. Record the measurements and the machine caveat in the audit.

### Runtime schema validation

Validate once per store instance, inside lazy connection setup, exactly as
both local backends do. Never validate per call, and never add a network
round trip to a routing decision for validation purposes.

On mismatch, raise the established mismatch error naming the backend, the
target (with credentials redacted), what was detected, what was expected, the
fact that nothing was altered, and the safe next action. A missing table is a
mismatch, not an invitation to create one.

### Connection configuration

The constructor takes a standard PostgreSQL connection string plus explicit,
individually configurable settings. Follow the repository's typed-model
convention for grouped configuration and validate at the constructor
boundary, raising from the existing error hierarchy for invalid values.

Timeouts default to connect 5 seconds, statement 2 seconds, pool checkout 2
seconds. Each is individually configurable. Document connect 10 / statement 5
/ checkout 5 as the completeness-first preset for slow or distant links, and
explain the trade plainly: short timeouts mean a provider call is never
noticeably delayed by bookkeeping but rows can be lost on a poor connection;
long timeouts mean complete history but a struggling database can add seconds
to a call and, because the router holds its lock across storage calls, stall
other threads while it does. The statement timeout is enforced server-side on
the session.

Pooling mode is one explicit setting with three values — direct, session
pooler, transaction pooler — defaulting to direct. The store configures
prepared statements and its own pooling to match: transaction-pooler mode
must disable server-side prepared statements. Never auto-detect the mode.
Because the wrong choice fails intermittently rather than obviously, detect
the specific prepared-statement failure and re-raise it with a message naming
the likely cause and the exact setting to change. Pool size defaults small
(roughly one to four connections) and is configurable; hosted plans have low
connection budgets and the router serializes its own storage calls anyway.

Encryption is required by default. Certificate verification is available and
documented, including how to supply a certificate authority file for hosted
providers. An unencrypted connection is refused unless explicitly overridden,
and the documentation must state plainly that the default encrypts without
verifying the server's identity.

Document the Supabase deployment shape specifically: direct versus session
versus transaction pooler connection strings and their ports, the interaction
between our pooling and an external pooler, prepared-statement restrictions,
certificate configuration, and separate administrator and runtime roles and
connection strings.

### Concurrency and lifecycle

The store holds no lock of its own. psycopg_pool is designed for concurrent
use from many threads, and the router already serializes its own storage
calls under the router lock, so a store-level lock would guard nothing the
router can do concurrently while adding a way for one slow direct read to
block all routing. Because the store takes no lock, the shipped
router-before-store lock-ordering rule cannot be violated here.

Document this deviation with its reason: the local backends lock because
their drivers cannot be shared across threads; this one does not because its
pool exists precisely to handle that.

`close()` is idempotent, disposes the pool, and permits lazy reconnection on
a later operation, matching the local backends. The store is always
caller-constructed and therefore caller-owned; the router never closes it.
Support use as a context manager if that reads naturally alongside the
existing stores, but do not make the store terminal.

### Writes

Provide a batch-write method on the concrete class that inserts many rows in
one round trip inside one all-or-nothing transaction, and implement the
ordinary single-attempt write in terms of it, so the batch path is exercised
by every write rather than shipped unused. The class may carry methods beyond
the protocol — both local stores already do — as long as the router requires
none of them.

Nothing else about writing changes. The router still hands over one attempt
at a time and that attempt is still written before the caller receives their
response. Do not add a buffer, queue, background thread, delayed flush,
retry loop, or any change to ordering, durability, or read-after-write
visibility. PR32 owns all of that and will find a backend that can already
accept a batch. Do not add batch writing to the local backends.

### Reads

`query_recent` keeps exact raw chronological semantics: the same filters, the
same ascending order, the same lower time bound, converted through the shared
record conversion.

`query_score_aggregates` must match the shipped aggregate contract exactly —
one bounded query, one row per distinct requested provider, the same
scope/provider/model/protocol/call-type/time partition, flat and exponential
weighting from the single supplied reference time, weighted attempt/success/
latency evidence as floats, exact unweighted error, rate-limit and timeout
tallies, explicit all-zero rows for genuine empty history, and the same
validation of missing, duplicate, unexpected, malformed, negative,
inconsistent, or non-integer results. The database never supplies its own
current time. Final scores never move into SQL. The pure reference
implementation in tests/metrics_store_helpers.py is the semantic oracle.

Provide the private explain helper the local backends have, so plans can be
measured deterministically.

### Failures and credentials

The store raises real driver and database errors and swallows nothing. The
router's existing per-write exception handling and the scoring policy's
existing fallback own graceful degradation and warning deduplication: an
unreachable database must still return the provider's response, and a failed
aggregate must still return the tie-break order. Do not add retries, silent
recovery, or degradation logic inside the store.

Connection strings, passwords, and bound parameter values must never appear
in exception messages, log records, or the object's repr. Redact the
credential portion everywhere a target is named, including administration and
CLI output.
